What the stronger comparison tells us

A carefully aligned crop also preserves the output and reduces the model workload. The added value of our software is choosing the original context automatically and limiting blending storage to the requested output. The table below shows the measured timings of both methods.

This is software correctness and efficiency. It does not establish better ink detection or new letters. “Temporary blending arrays” means working files used to combine overlapping predictions; the model's own memory is separate.

What can someone do with it?

Ask for a local prediction

Keep the original scan array and supply the rectangle you want to inspect. The API retains the original contributing windows and their overlap weights, then writes a PNG or NPY for that rectangle with coordinate metadata.

This could support local annotation checks or inspection of a suspected stroke. An integration into a community viewer and measured annotation-time savings remain to be demonstrated.

See why cropping only the desired input area can change predictions

Understand the specific benefit

A careful context crop is a valid alternative in these batch-one tests. Our interface automates the selection and keeps the output accumulators small. The original eight-case study also checks 3D outputs, depth direction and preservation of original batch groups.

The underlying global-grid principle predates this work. Villa PR #1247 and existing Hecate optimizations are credited. No broad novelty or fastest-reader claim is made.

Reproduce the evidence

Check the saved package

python3 verify_repeats.py

Uses Python's standard library, with no model or package download. It checks the file hashes, original results, all new regional/context-crop values, repeat consistency and the arithmetic of the reported timings and storage.

A saved-file check cannot independently measure runtime or verify physical ink.

Run fresh inference

Install the pinned environment, obtain the hash-checked Hecate weights and run the portable worker commands in the README. Inputs and exact settings for all five workers are included.

Weights are approximately 523 MB per resolution. Use a new output directory and keep all results, including slow or differing ones.

Study scope and limitations

Three existing exposed physical fields from PHerc841, PHerc9B and PHerc500P2. Two fine-resolution central requests; edge, centre and large requests on three coarse inputs. Four CPU threads, float32, batch one, unchanged model weights, three balanced repeats. Coarse inputs use fixed 4×4×4 averaging and rounding. No labels or reserved reading-final regions were used.

The reference is the original runtime on the supplied parent field, not an entire scroll or physical ink truth. Coarse requests share a full-field timing within each repeat. Three repeats describe local variation, not a population confidence interval. Independent hardware, GPU/cloud performance and community use have not been verified.

A clean environment and portable tests passed, and local Zarr v2 loading/CLI scheduling matched NPY. Existing earlier reading experiments that failed remain negative results; this software comparison does not turn them into new ink recovery.
